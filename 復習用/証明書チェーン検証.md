# 証明書チェーン検証

これは、HTTPS通信の開始時に行うTLSハンドシェイクのうち、ブラウザがWebサーバ証明書を検証してサーバ認証を行う部分を取り出した図です。TLS全体の流れは [TLS 1.3ハンドシェイク](TLS1.3ハンドシェイク.md) を参照してください。

```mermaid
sequenceDiagram
    participant Browser as ブラウザ
    participant Server as Webサーバ（server.example.jp）
    participant Store as ブラウザの信頼ストア

    Browser->>Server: ブラウザがHTTPS接続を開始する
    Server-->>Browser: Webサーバがサーバ証明書と中間CA証明書を送付する
    Browser->>Store: ブラウザが信頼済みルートCA証明書を取得する

    Browser->>Browser: サーバ証明書のtbsCertificateをハッシュ化してh1を計算する
    Browser->>Browser: 中間CA証明書内の公開鍵でサーバ証明書の署名を検証する
    alt h1と署名が対応しない
        Browser-->>Server: ブラウザが警告を出し、接続を失敗させる
    else h1と署名が対応する
        Browser->>Browser: 中間CA証明書の署名対象をハッシュ化してh2を計算する
        Browser->>Browser: ルートCA公開鍵で中間CA証明書の署名を検証する
        alt h2と署名が対応しない
            Browser-->>Server: ブラウザが警告を出し、接続を失敗させる
        else チェーンの署名が有効
            Browser->>Browser: サーバ証明書の有効期限とSANを確認する
            alt 有効期限切れ、またはSAN不一致
                Browser-->>Server: ブラウザが警告を出し、接続を失敗させる
            else 有効期限内、かつSANにserver.example.jpを含む
                Browser->>Server: ブラウザが証明書を信頼し、TLS通信を継続する
            end
        end
    end

    Note over Browser,Store: ルートCAは信頼ストアにあらかじめ登録され、信頼の起点となる
    Note over Server,Browser: 必要な中間CA証明書をWebサーバが送らないと、ブラウザはチェーンを構築できず接続に失敗し得る
```

RSA署名なら「発行者の公開鍵で署名からハッシュ値相当を得て照合する」と簡略化して考えられます。ECDSAなどでは、公開鍵・署名値・計算したハッシュ値を使い、署名が対応するかを真偽で判定します。いずれの場合も、比較するのは**サーバ証明書と中間CA証明書そのものではなく**、サーバ証明書から計算したハッシュ値と、その署名の検証結果です。
