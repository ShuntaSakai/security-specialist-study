## 学んだことの殴り書き

### 暗号化と署名は違う

- 暗号化の目的は「中身を読めなくすること」。

- 署名の目的は「誰が作ったか・改ざんされていないかを確認すること」

### サーバ証明書に入っている主な内容

**証明書（Certificate）の中には、CAが署名する対象である `tbsCertificate` と、その対象に対するCAのデジタル署名である `signatureValue` の両方が入っている。**

```text
Certificate
├─ tbsCertificate  ← CAが署名する対象部分
│  ├─ シリアル番号
│  ├─ 署名アルゴリズム
│  ├─ Issuer（発行したCA）
│  ├─ 有効期限（Not Before / Not After）
│  ├─ Subject（証明書の対象者）
│  ├─ サーバの公開鍵
│  ├─ 公開鍵アルゴリズム
│  └─ 拡張情報
│     ├─ SAN（利用を許可するドメイン名）
│     └─ Extended Key Usage（例: serverAuth）
│
├─ signatureAlgorithm  ← CAが署名に用いたアルゴリズム
└─ signatureValue      ← tbsCertificateに対するCAのデジタル署名
```

- `tbsCertificate` は「署名対象部分」であり、CAの署名値そのものではない。ブラウザはここをハッシュ化し、`signatureValue` を発行者CAの公開鍵で検証して対応を確認する。
- `signatureAlgorithm` は、`tbsCertificate` 内にも署名アルゴリズム情報として含まれる。外側の `signatureAlgorithm` と整合していることも確認対象である。
- Webサーバの接続先名は、現在では主にSANで確認する。Subjectだけで接続先名を判断しない。
- ブラウザは署名に加え、有効期間、SANの接続先名一致、証明書チェーン、必要に応じて失効状態を確認してから証明書を信頼する。

### TLSで「相手を信頼して通信を続ける」流れ

```text
1. 証明書でWebサーバの身元を確認する
2. ECDHE鍵交換で、双方が同じ共有秘密をそれぞれ計算する
3. 共有秘密から通信ごとの鍵を導出し、以後のデータを暗号化・認証する
```

- 「共通鍵を持っていること」だけが身元証明なのではない。最初に証明書と `CertificateVerify` でWebサーバの身元と秘密鍵の保持を確認する。
- TLS 1.3では、Webサーバの公開鍵で共通鍵を暗号化して送るわけではない。公開鍵暗号技術の一種であるECDHE鍵共有を使い、ブラウザとWebサーバが一時公開鍵を交換して、双方が自分の一時秘密鍵と相手の一時公開鍵から同じ共有秘密を計算する。共通鍵そのものはネットワーク上を送らない。
- ブラウザは証明書検証に成功してから、その共有秘密から導出した鍵を「認証済みのWebサーバとの通信鍵」として受け入れる。
- 以後はAES-GCMやChaCha20-Poly1305などのAEADで、暗号化と改ざん検知用の認証タグをセットで使う。受信側は、正しい通信鍵を知る相手だけが作れる認証タグを検証する。
- 感覚的には、最初に証明書で「あなたは誰か」を確認し、その後は「二人だけが導出した通信鍵で正しい認証タグを作れているか」を確認し続ける。これにより、同じ認証済み相手との通信が継続していることと、途中改ざんがないことを確かめる。

### HTTPとHTTPSの違い

| 性質 | HTTP | HTTPS（HTTP over TLS） |
|---|---|---|
| 機密性 | 通信内容を暗号化しないため、途中で読まれ得る | TLSで通信内容を暗号化する |
| 完全性 | 改ざんされても検知できない | AEADの認証タグなどで改ざんを検知する |
| サーバ認証 | 接続先が本物のサーバか確認できない | 証明書で、接続先ドメイン用の秘密鍵を持つサーバか確認する |

- HTTPでは盗聴だけでなく、攻撃者が途中で応答を書き換えたり、偽サーバへ誘導したりできる。
- 通常のHTTPSが主に認証するのはサーバ側である。利用者側の本人確認は、ログインや必要に応じたクライアント証明書で別に行う。

### TLSはHTTP専用ではない

TLSはHTTPだけの技術ではなく、上位プロトコルの通信を暗号化・改ざん検知・相手認証で保護するための汎用的な層である。典型的には、アプリケーションプロトコルの下、TCPの上で使われる。

| 上位プロトコル + TLS | 代表的な用途・呼び名 |
|---|---|
| HTTP + TLS | HTTPS |
| SMTP + TLS | メール送信経路の保護 |
| IMAP / POP3 + TLS | メール受信の保護 |
| LDAP + TLS | LDAPSなど、ディレクトリサービス通信の保護 |
| FTP + TLS | FTPS |

- SMTP、IMAP、POP3、LDAPなどでは、最初からTLSで接続する方式のほか、平文接続後に `STARTTLS` でTLSへ切り替える方式もある。
- TLSが保護するのは通信路であり、各アプリケーションの認証・認可の設計そのものを置き換えるものではない。

### SQLインジェクションでいう「文字列連結」

- `+` 演算子の有無ではなく、**外部入力をSQL文のテキストへ直接組み込むこと**を指す。テンプレートリテラルや文字列補間でも同じく危険になり得る。
- 入力値を `'` で囲んでいても、SQLとして解釈される箇所に組み込む限り安全ではない。
- 対策は、SQL文と値を分離するプレースホルダ（プリペアドステートメント）を使うこと。
- プレースホルダは「ここから来るのは**値**」という値用の席（場所を確保する印）。先にSQLの構文を確定させ、後から渡す値をSQL構文として再解釈させない。単純な文字列置換ではない。

```js
// 危険：+ でなくても、入力値をSQL文に埋め込んでいる
`SELECT * FROM users WHERE name = '${input}'`

// 安全：? は値用の席。input はSQL文と別に値として渡す
db.query('SELECT * FROM users WHERE name = ?', [input])
```

- ただし、表名・列名・`ORDER BY` の順序などのSQL構文はプレースホルダにできない。利用者に選ばせる場合は、許可リストから固定の候補を選ぶ。

### DNSSECのRRSIG検証

- `RRSIG`は自分で検証するものではない。キャッシュDNSサーバの検証処理が、受信DNSデータ・`RRSIG`・`DNSKEY`（公開鍵）を使い、署名が有効かを判定する。
- 署名側は、正規化したDNSレコード群などの署名対象をハッシュ化して指紋`A`を作り、秘密鍵で署名して`RRSIG`を作る。検証側は受信データから指紋`A'`を作る。
- RSA方式では、「公開鍵で`RRSIG`を処理して署名時の指紋`A`に対応する値を確認し、`A'`と照合する」と考えてよい。ただし、元のDNSデータを復元する処理ではない。
- ECDSAやEd25519では、`RRSIG`を指紋`A`へ戻さない。公開鍵・`RRSIG`・指紋`A'`を使う数式で、直接`OK / NG`を判定する。
- 方式が異なっても目的は同じで、**「この受信DNSデータに対応する署名か」**を検証すること。`RRSIG`と`DNSKEY`にあるAlgorithm番号から、使う検証方式を判断する。
- 2026-08時点で代表的に推奨される方式は、`8: RSASHA256`、`13: ECDSAP256SHA256`、`15: ED25519`。ルートゾーンのKSKは同時点で`8: RSASHA256`を使用している。
